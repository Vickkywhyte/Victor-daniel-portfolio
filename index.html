№ 03 — Technical AI Competencies

Seven capabilities, organised by the order in which they matter.

i. Design — deciding what to build, and what not to build

Use-case evaluation

Identifying when AI genuinely adds value versus when a deterministic rule, a SQL query, or a simpler automation does the same job with less risk. The first decision is whether to use a model at all.

Model & cost selection

Choosing between model tiers based on task complexity, latency requirements, and budget — routing easy queries to cheaper models and reserving frontier models for what genuinely demands them. Cost discipline as a design constraint.

ii. Build — making systems do what they are supposed to do

Prompt engineering for structured outputs

Designing prompts that produce consistent, parseable outputs from LLMs — schemas, decision objects, structured rationales — so the model becomes a reliable component in a larger system rather than a wildcard.

Retrieval-augmented generation

Hands-on RAG: chunking strategy, retrieval (TF-IDF and vector), grounding, attribution, and the trade-offs between recall, precision, and answer faithfulness. Shipped multiple RAG systems including CGSS sanctions, HR policy, and EDD QA.

Agent system design

Understanding how agent loops actually work — Observe-Reason-Act, scratchpads, tool use, max-iterations — and the failure modes they introduce. Building with scope constraints, validation gates, and escalation paths from day one, not as a retrofit.

iii. Secure — assuming the inputs are hostile

AI security & defence-in-depth

Recognising prompt injection in retrieved documents, tool outputs, and user inputs. Designing layered defences — sanitisation, scope guards, output validation, irreversible-action gates — on the assumption that any one layer will eventually fail.

iv. Evaluate — knowing whether the system actually works

Reliability assessment

Applying the Trust Checklist before deployment — grounding, attributability, stress-testing for hallucination, human-in-the-loop, feedback loops, out-of-scope behaviour, and drift monitoring. A "?" is treated as a risk, not a to-do.

№ 05 — Deployment Standards

What the Trust Checklist actually means in practice.

These are not aspirations. They are the conditions under which I will and will not put a system in front of users. Each one corresponds to a specific item on a pre-deployment checklist I have learned to take seriously.

i.

I do not deploy systems that hallucinate without detection.

If a factual claim cannot be traced to a verified source, the system does not ship. Grounding and attribution are not features — they are the precondition for the system existing at all.

ii.

A "?" is a risk, not a to-do.

Unknown answers on a pre-deployment review are unacknowledged risks. They are resolved before deployment, not after the first incident.

iii.

Irreversible actions require human approval.

Sending a message, modifying a record, executing a transaction — these are gated. Not optionally. The gate is a mandatory pause point, not a checkbox the user has to opt into.

iv.

Agents have explicit scope. So do I.

"Be helpful" is not a scope constraint. Every agent I build has an explicit list of what it is authorised to do and what it is not, and an escalation path for the case where the goal requires stepping outside it.

v.

External inputs are hostile until proven otherwise.

Retrieved documents, tool outputs, user submissions — all of it is sanitised before reaching the model. Prompt injection is treated as a real failure mode, not a hypothetical.

vi.

The stress test happens before the user does.

Out-of-scope inputs, post-cutoff questions, deliberately ambiguous prompts — these are run through the system on purpose, before deployment. If no one has tried to make the system fail, it will fail in production.

vii.

Monitoring is the system, too.

Iteration counts, tool success rates, escalation rates, output quality. A deployment without a monitoring plan is a deployment without a way to know whether it is still working.

viii.

Passing every check is not a guarantee of correctness.

It is a system designed to catch and correct errors. That is the entire goal. The discipline is what makes the system survivable when it inevitably surprises me.

№ 06 — Quick Reference

The seven failure modes I design against.

Hallucination
Every factual claim must trace to a specific source passage. Ungrounded systems are not deployed. Stress-tested against post-cutoff and out-of-corpus prompts before going live.
Trust · 01–03
Irreversibility
Sending, modifying, deleting, transacting — all gated behind mandatory human approval. The gate is not optional. Asynchronous approval is fine; bypass is not.
Trust 04 · Agent 03
Cascading errors
Tools tested in isolation before integration. Tool outputs validated before use in subsequent reasoning. Intermediate steps logged so root-cause is recoverable. Confidence thresholds for escalation.
Agent · 04, 07, 09
Scope creep
Scope defined explicitly in the system prompt — what is permitted and what is forbidden. Out-of-scope queries trigger declined behaviour or escalation, not silent attempts to comply.
Trust 06 · Agent 01, 08
Prompt injection
All external inputs — retrieved documents, tool returns, user content — sanitised before entering model context. Treated as the primary attack surface for agentic systems, not an edge case.
Agent · 02
Undetected failure
Max-iteration caps with defined behaviour on hit. User feedback loops as a minimum viable detection mechanism. Confidence-triggered escalation paths rather than confident wrong answers.
Trust 05 · Agent 05, 06
Drift & degradation
A monitoring plan with defined metrics, thresholds, and response actions. Models do not degrade themselves; the world they answer about does. The plan is for detecting that gap.
