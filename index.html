03 · Competencies

Seven capabilities, in the order they matter.

Design decides what to build. Build makes it work. Secure assumes the inputs are hostile. Evaluate tells you whether any of it is true.

i
Design

Deciding what to build, and what not to.

Use-case evaluation

Identifying when AI genuinely adds value versus when a deterministic rule, a SQL query or a simpler automation does the same job with less risk. The first decision is whether to use a model at all.

Model & cost selection

Choosing between model tiers on task complexity, latency and budget, routing easy queries to cheaper models and reserving frontier models for what demands them. Built into a router that logs cost and quality per request.

ii
Build

Making systems do what they are supposed to do.

Prompt design for structured outputs

Prompts that produce consistent, parseable outputs, such as schemas, decision objects and structured rationales, so the model is a reliable component in a larger system rather than a wildcard.

Retrieval-augmented generation

Hands-on RAG: chunking, retrieval with TF-IDF and vectors, grounding, attribution, and the trade-offs between recall, precision and faithfulness. Shipped across sanctions training, HR policy and company documents.

Agent system design

How agent loops actually work, observe-reason-act, tool use and max-iterations, and the failure modes they bring. Built with scope constraints, validation gates and escalation paths from day one, not as a retrofit.

iii
Secure

Assuming the inputs are hostile.

AI security & defence-in-depth

Recognising prompt injection in retrieved documents, tool outputs and user inputs. Layered defences, sanitisation, scope guards, output validation and irreversible-action gates, on the assumption that any one layer will eventually fail. Applied as a STRIDE threat model with tested injection scenarios.

iv
Evaluate

Knowing whether the system actually works.

Reliability assessment

A trust checklist before deployment: grounding, attribution, hallucination stress-testing, human-in-the-loop, feedback loops, out-of-scope behaviour and drift. Backed by golden datasets, claim-level hallucination scoring, refusal correctness and bootstrap confidence intervals on every aggregate.

04 · Systems

Systems I have built.

The first two work as a pair: the runtime governs what an AI agent may do, and the harness proves the runtime did it. All four are MIT licensed and cost nothing to run.

Flagship · pairs with the harness

Open-source runtime

Compliance Runtime

Sits between an AI agent and its tools. Every tool call is allowed, denied, flagged or sent to a person for approval before it runs.

Firms are giving agents real actions such as refunds and record changes, and the EU AI Act asks them to log those actions and keep humans in charge (Articles 12 and 14). This runtime decides with plain rules, keeps every LLM out of the decision, and records each outcome in a signed, hash-chained log that exports as a PDF dossier.

  • 17 evaluation metrics with bootstrap confidence intervals, no LLM calls
  • Missing or invalid fields are denied, never guessed
  • Concurrent approvals resolve to exactly one decision

Python · FastAPI · SQLite · Ed25519 · Streamlit · Docker

Flagship · proves the runtime

Independent verification

Governance Measurement Harness

Tests whether the runtime's policies actually work, and gives an auditor a way to check the results on their own machine.

It runs labelled cases through the live policy engine: actions that should be refused, allowed, escalated or flagged. Each result is written into the same signed chain. The verifier needs only Python and one cryptography library, and imports nothing from my code, so the auditor does not have to trust it.

  • Reports accuracy, missed blocks and unnecessary blocks separately
  • A tamper mode flips one byte and shows the whole chain fail

08 · Deployment standards

What the trust checklist means in practice.

These are not aspirations. They are the conditions under which I will and will not put a system in front of users. Each maps to an item on a pre-deployment checklist I have learned to take seriously.

  • i
    I do not deploy systems that hallucinate without detection.If a factual claim cannot be traced to a verified source, the system does not ship. Grounding and attribution are the precondition for the system existing at all.
  • ii
    A “?” is a risk, not a to-do.Unknown answers on a pre-deployment review are unacknowledged risks. They are resolved before deployment, not after the first incident.
  • iii
    Irreversible actions require human approval.Sending a message, modifying a record, executing a transaction. These are gated. The gate is a mandatory pause point, not a checkbox the user opts into.
  • iv
    Agents have explicit scope. So do I.“Be helpful” is not a scope constraint. Every agent has an explicit list of what it may and may not do, and an escalation path for when the goal needs more.
  • v
    External inputs are hostile until proven otherwise.Retrieved documents, tool outputs and user submissions are sanitised before reaching the model. Prompt injection is treated as a real failure mode, not a hypothetical.
  • vi
    The stress test happens before the user does.Out-of-scope inputs, post-cutoff questions and deliberately ambiguous prompts are run through the system on purpose, before deployment.
  • vii
    Monitoring is the system, too.Iteration counts, tool success rates, escalation rates, output quality. A deployment without a monitoring plan has no way to know whether it is still working.
  • viii
    Passing every check is not a guarantee of correctness.It is a system designed to catch and correct errors. That discipline is what makes it survivable when it inevitably surprises me.
